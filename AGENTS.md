# Hermes plugin agent memory

- This repository is a POM `cdylib` plugin scaffolded from `creating-pom-plugins`; contract details are in the POM repository's `docs/subsystems/plugins-ui.md` and `enterprise-licensing.md`. `src/abi.rs` is the panic-safe C ABI; `src/lib.rs` dispatches requests. Never block `query` (3-second IPC timeout).
- `src/supervisor.rs` owns background children and the supervised bridge. `src/installer.rs` downloads and SHA-256 verifies the pinned Hermes tarball and platform-specific uv, extracts only regular files with confined paths, installs managed Python 3.14.9, delegates dependencies to upstream `pm.cli install`, and calls upstream `hermes_cli/source_completion.py` to build TUI/web and sync config and skills. No Python, bash, Git, curl or Node from the host is required for first install. Do not replace Hermes PM with `pip install` or system Node; its source rejects wheels. `runtime.py` only launches the managed dashboard and acts as the per-launch authenticated loopback bridge. The plugin is `lifecycle: on_demand`: POM starts the host from the menu (`host.configure` relaunches an existing install) and the menu X stops it. Closing must leave nothing behind, and Hermes detaches on purpose (its `gateway run` daemon via `start_new_session`, each chat TUI in its own session), so `killpg` on the dashboard is not enough. On Linux the bridge is `PR_SET_CHILD_SUBREAPER`, so those orphans are reparented to it and reaped there; on close (stdin EOF from the supervisor, or SIGTERM from PDEATHSIG) `stop_hermes` SIGTERMs every live descendant plus the gateway in `HERMES_HOME/gateway.pid` (the only way to find it on macOS and Windows, where Windows uses `taskkill /T /F`), SIGKILLs survivors after 2 s and logs one line to `bridge.log`. The supervisor waits 5 s for that before killing the bridge. A standalone Linux install with system Python/Git/curl/Node/npm masked and a live dashboard root and `/api/status` was verified locally. The on-demand smoke workflow completed the same full install and live dashboard test on native macOS and Windows runners; Windows also produced a release-mode `.dll`. Regular CI compiles/tests Linux, macOS and Windows.
- POM strips browser Authorization. The bridge verifies `x-pom-plugin-token` from POM *before* adding its own per-launch Hermes auth; it rewrites Host for Hermes's loopback guard and sends `X-Forwarded-Prefix` for its prefixed SPA. POM forwards header names in lowercase, so the WebSocket path matches `Upgrade`/`Origin` case-insensitively and sends each once: a duplicated `Upgrade` makes uvicorn answer 426 and breaks `/api/ws`, `/api/events` and `/api/pty` (the chat side panel and terminal). Do not forward browser cookies or secrets. `rpc.status` and `host.services` never include private tokens, ports, or gateway keys. The dashboard route is `full_bleed` and, once ready, the screen is only the borderless iframe; there is no POM header around it.
- The screen (`ui/src/screens/Main.tsx`) draws no loading or setup state: it requires POM host version 7 and maps `rpc.status` to POM's loader (`loader` and `onLoaderRetry` in `ui/src/host/runtime.ts`). `loader.show` on the first render; `waiting` calls `rpc.install` once; `installing` is `loader.progress` with the step's message (title "Updating" when `mode` is `update`); `starting` is the generic loader, or the bar held at 100 after an install in this mount; `ready` mounts the iframe and its load sends `loader.success` after an install or `loader.hide` otherwise; `error` is `loader.error` ("Hermes Agent stopped" once the dashboard was shown), and `loader.retry` calls `rpc.install` again. The screen no longer sends a model; `rpc.install` still accepts `model` for the call shape.
- Install progress: `installer::install_mode` tells a fresh install and an update (marker missing, other pinned sha, or no dashboard build) from an installed Hermes. Only the first two put `rpc.status` in `installing`; starting an installed one goes straight to `starting`, even though `ensure` still checks the web build. While installing, `ensure` reports each `installer::Step` (`source`, `uv`, `python`, `packages`, `dashboard`, then `connect` for `register_pom`) and the downloads report their byte fraction. `rpc.status` then carries `step`, `progress` and `mode` (`install`/`update`); `supervisor::progress_at` computes the bar at read time, so the creep needs no timer: each step owns a fixed share, a download follows its bytes and any other step eases toward 95% of its share with time, never reaching its end before it finishes.
- The dashboard's Vite bundle is rebuilt by `installer.rs` with `base: "/api/ui/plugins/hermes/proxy/"` (marker `.pom-prefixed-web-v1`): every `/assets/*` URL goes through the proxy. A plain upstream build without that base 404s the chunks when POM serves the screen. Do not revert that patch or the config anchor check that guards it.
- POM models: `installer::register_pom` runs `pom_provider.py` under Hermes's own configuration API after install/startup. It registers `providers.pom` (`name: POM`, `base_url: <node loopback>/v1`, `key_env: POM_API_KEY`) and stores the gateway key only in Hermes's owner-only `.env` as `POM_API_KEY`; it never touches `model.default` and refuses to overwrite a user-owned `pom` provider. It caches `/v1/models` ids as metadata (not an allowlist); Hermes's picker refreshes them live on explicit refresh. An offline gateway still registers the provider.
- Fixed files, source, logs and PM tools live next to `POM_PLUGIN_DB` under `hermes/`. Hermes user data (`HERMES_HOME`) is under `workspace_root/.hermes/` (fallback to runtime `data/`), and the dashboard runs with `workspace_root` itself as its cwd, so the default `terminal.cwd: "."` points the agent at POM's workspace and never at Hermes's own `source/` (`PYTHONPATH` finds the code). Hermes's own detached `gateway run` daemon (messaging, cron) still starts in `source/` and strips `TERMINAL_CWD` upstream; only an absolute `terminal.cwd` in its config moves it. Only the first setup may create a POM model config; existing Hermes settings are never overwritten. The Hermes dashboard itself handles later changes, including POM API key rotation.
- `ui/manifest.json` and `release/manifest.json` are separate. UI reads `__POM_HOST__` only in `ui/src/host/*`; the `pb-` CSS prefix is renamed to `hermes-` during the build. `scripts/dev-ui.sh` writes outside the read-only dev source mount. The plugin icon (`ui/icon.png`) is the official Hermes app icon from the pinned upstream commit's desktop assets.
- Verify with `scripts/build-ui.sh`, `POM_UI_REQUIRE_DIST=1 cargo test --locked`, `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `python3 -m unittest discover -s tests -p 'test_*.py'` (bridge and `pom_provider`), and `tests/test_ci_plan.sh`. The ignored `cargo test --locked installer::tests::installs_without_system_python_git_or_curl -- --ignored --nocapture` performs a full install and tests the live authenticated dashboard; it requires network, several gigabytes and time. `.github/workflows/installer-smoke.yml` runs it on demand on Windows, macOS or Linux. Release packaging supports all three.
